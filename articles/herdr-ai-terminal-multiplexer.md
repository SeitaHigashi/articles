## はじめに

`tmux`・`screen`・`zellij` といったターミナルマルチプレクサを使い込んでいる方なら、Claude Code や Codex、Cursor CLI のようなAIコーディングエージェントを複数のペインに並べて動かした経験があるのではないでしょうか。

ただ、この使い方には地味な不便さがあります。

- どのペインのエージェントが「作業中」で、どれが「入力待ち」なのか、いちいち切り替えて確認しないと分からない
- ラップトップをスリープさせたりSSHが切れたりすると、セッションの扱いに気を使う
- エージェント自身がペインを分割したり別のエージェントの出力を読んだりといった、エージェント発の操作がしづらい

この記事では、こうした「AIエージェントを前提にしたターミナルマルチプレクサ」というコンセプトを掲げるツール **Herdr** を紹介します。筆者もまだ使い始めて間もないため、深い実運用レポートというよりは「どんなツールで、何が既存のマルチプレクサと違うのか」を紹介する導入記事として読んでいただければと思います。

:::message alert
筆者はHerdrをまだ触り始めたばかりで、長期運用での知見は持っていません。本記事の情報は公式サイト・公式リポジトリおよび第三者の解説記事の調査に基づくもので、実際に手元で動かして検証した内容ではない箇所が含まれます。導入の際は必ず公式ドキュメント([herdr.dev](https://herdr.dev/))で最新情報をご確認ください。

## Herdrとは何か

Herdrは、Rust製・Ratatui(TUIライブラリ)ベースで実装された、ターミナルネイティブな「エージェントランタイム兼マルチプレクサ」です。公式サイトのタグラインは次のように紹介されています。

> The runtime your coding agents live on — laptop, desktop, or a box you rent.

`tmux` や `zellij` と同じく、ペイン・タブ(ワークスペース)・セッションの永続化というモデルを踏襲しつつ、そこに「AIコーディングエージェントの状態把握」という軸を足したツール、というのが実態に近い理解です。

### tmux/screen/zellijとの違い

既存のマルチプレクサは、ペインの中で動いているプロセスが何であるかを区別しません。シェルだろうがビルドプロセスだろうがAIエージェントだろうが、ただの「ターミナル出力」として扱われます。

Herdrはここに手を入れていて、Claude Code・Codex・Cursor・opencode・Grok(記事執筆時点で公式が言及している対応エージェントの例)などのエージェントCLIをペイン内で検出し、そのペインが

- `working`(処理中)
- `idle`(入力待ち)
- `blocked`(ユーザーの応答待ちで止まっている)

のどの状態かをサイドバーに表示してくれます。複数のエージェントを並列で走らせているとき、「どのペインが止まっているか」を一目で把握できるのが最大の売りです。

また、Herdr自体がCLIとローカルソケットAPIを備えており、エージェントのプロセス自身がHerdrを操作できる(ペインを分割する、他のエージェントの出力を読む、など)点も特徴として挙げられています。ここは通常の `tmux` にはない発想で、「エージェントがマルチプレクサを自己駆動する」ことを前提にした設計だと言えます。

## 主な特徴

調査した範囲でまとまっている特徴を整理します。

- **クライアント/サーバー構成**: バックグラウンドのセッションサーバーがPTYセッションを管理し、ラップトップのスリープ・WiFi切断・SSH切断をまたいでセッションが生き続ける。クライアント(ターミナルウィンドウ)とはローカルUnixソケット、あるいはSSHトンネル経由で通信する
- **エージェント状態の可視化**: 上述の `working` / `idle` / `blocked` をサイドバーに表示
- **マウス操作**: クリックでペインにフォーカス、ドラッグでリサイズ、右クリックでコンテキストメニューといったマウスファーストな操作にも対応(キーボードだけで完結する `tmux` スタイルの操作も可能)
- **tmux互換のプレフィックスキー**: デフォルトは `ctrl+b`。`tmux` に慣れたユーザーがそのまま移行しやすいように意識されている
- **リモート対応**: `herdr --remote ssh://user@host` のようにリモートサーバー上でセッションサーバーを動かし、ローカルの設定を保ったままリモートに接続できる
- **プラグイン/マーケットプレイス**: ローカル実行形式のプラグインとイベントフックの仕組みがあり、GitHub経由でコミュニティのプラグインを共有できる
- **単一のRustバイナリ**: Electron等の重量級ランタイムに依存せず、単一バイナリで配布される。ライセンスはApache 2.0

## インストール

公式サイト([herdr.dev](https://herdr.dev/))によると、インストール方法は複数用意されています。

macOS/Linuxはスクリプト経由:

```bash
curl -fsSL https://herdr.dev/install.sh | sh
```

Homebrewでも導入できるとされています。

```bash
brew install herdr
```

Windowsの場合はPowerShellから。

```powershell
irm https://herdr.dev/install.ps1 | iex
```

対応プラットフォームはmacOS・Linux・Windowsで、公式にサポートが明記されています。

## 基本的な使い方(公式情報ベース)

インストール後は、プロジェクトのディレクトリで `herdr` を実行するだけで起動します。

```bash
herdr
```

セッションから抜けたいときは `tmux` と同様にデタッチ操作(`ctrl+b` に続けて `q` など)を使い、再度 `herdr` を実行すれば同じセッションに再アタッチできます。セッションはバックグラウンドのサーバープロセスが保持しているため、ターミナルを閉じてもエージェントの作業自体は継続する、という理屈です。

設定ファイルは `~/.config/herdr/config.toml` に置かれ、プレフィックスキーの変更などができるようです。

```toml
[keys]
prefix = "ctrl+space"
```

テーマはCatppuccin・Gruvbox・Nord・Draculaなどが組み込みで用意されている、と紹介されています。

:::details Herdr独自のCLI操作(調査ベース、未検証)
外部プロセスやエージェント自身がHerdrを操作するためのサブコマンドとして、`herdr pane split-right` や `herdr agent read` のようなコマンド例が第三者の解説記事で紹介されていました。エージェントに「作業結果を別ペインに表示しつつ、自分でペインを分割・集約する」といった振る舞いをさせたい場合に使うものと推測されますが、公式ドキュメントの一次情報では具体的なサブコマンド一覧までは確認できておらず、この部分は未検証の情報として扱ってください。

## プラグインエコシステム比較(tmux/zellij vs Herdr)

:::message
このセクションは、レビュー段階で「tmux/zellijのプラグイン運用とどちらが便利か」という関心が寄せられたことを受け、AIが追加で調査した内容を追記したものです。他のセクション同様、公式ドキュメント・第三者記事の調査に基づく情報であり、実機での検証は行っていません。
:::

`tmux` と `zellij` は、どちらもプラグインによって機能を拡張できますが、仕組みは大きく異なります。

- **tmux(TPM: Tmux Plugin Manager)**: プラグインの実体はシェルスクリプトで、`tmux` のCLIコマンドを叩いて動作します。約20年の歴史があり、`tmux-resurrect`(セッションの永続化)のような定番プラグインを含め、エコシステムの層が非常に厚いのが特徴です。一方で、プラグインはシェルスクリプトをそのまま読み込む形式のため、プラグイン自体がクラッシュしたり予期しない挙動をしたりするリスクを止める仕組みはあまりありません。
- **zellij**: プラグインはWASM(WebAssembly)モジュールとして動作し、Rust・Go・Cなど、WASMにコンパイルできる言語であれば書けます。サンドボックス化されているため、プラグインが本体をクラッシュさせにくいという安全性の面でのメリットがある一方、エコシステムの規模はtmuxに比べるとまだ小さいとされています。
- **Herdr**: プラグインはローカル実行形式で、マニフェストファイル(`herdr-plugin.toml`)を含むGitHubリポジトリに `herdr-plugin` というトピックタグを付けることで、マーケットプレイスに自動的に登録される仕組みのようです。公式サイトの記載では数百件規模のプラグインが登録されているとのことですが、この数値は変動が速く、また公式による審査(レビュー)は行われていない旨も明記されています。

:::message alert
Herdrのプラグイン件数やマーケットプレイスの実態は、執筆時点の公式サイトの記載に基づく未検証の情報です。tmux/zellijとの比較についても、AIによる調査結果であり実際に3ツールを並べて動作検証したものではありません。導入を検討する際は、各プラグインの信頼性(Herdrは公式審査なしと明記されている点に特に注意)を含め、必ずご自身で確認してください。
:::

大まかな傾向として、「枯れた実用性・数の多さで選ぶならtmux」「安全性(サンドボックス)を重視するならzellij」「AIエージェントの状態管理と統合されたワークフローを求めるならHerdr」という棲み分けになりそうですが、これはあくまで現時点の調査に基づく仮説であり、実際にプラグインを使い込んだ上での比較ではない点にご留意ください。

### tmux/zellijに「Herdr相当のエージェント状態トラッキング」プラグインはあるか

Herdrの最大の売りは「AIエージェントごとの working / idle / blocked 状態をサイドバーに表示する」機能ですが、これに相当する機能をtmux/zellijでもプラグインとして後付けできないか、という観点でも調べてみました。結論としては、**同種のコンセプトのサードパーティ製プラグインは複数存在します。**

**tmux向け**
- `tmux-agent-indicator`: 各ペインのAIエージェントを `running` / `needs-input` / `done` の3状態で分類し、ペイン枠線・ウィンドウタイトルの色・ステータスバーのアイコンで可視化します。Claude Code・Codex・OpenCode・カスタムエージェントに対応。エージェント側のフック(プロンプト送信・許可要求・停止コマンドなどのイベント)を主な検知手段とし、フック未対応のエージェントに対してはプロセス検知にフォールバックする方式のようです。
- `tmux-agent-sidebar` / `tmux-agent-status`: セッション横断でAIエージェント(Claude Code、Codex、OpenCodeなど)の Working / Blocked / Idle をサイドバー表示する、より「Herdrのサイドバー」に近いコンセプトのプラグインです。

**zellij向け**
- `zellaude`: Claude Codeセッションの活動状況をタブに表示するWASMプラグインで、状態の色分け、待機中セッションへの自動フォーカス、権限確認発生時のフラッシュ通知などを備えています。
- `zellij-attention`: Claude Codeのフック(`Notification` / `Stop` イベント)からパイプメッセージを受け取り、対応するタブに「待機中」「完了」の通知アイコンを付与するプラグインです。
- `zj-agents`: プロセス・画面出力から Idle/Working/Blocked/Done を分類し、フローティングサイドバーで表示するエンジンで、Claude・Codex・Grok・Piなど複数エージェントに対応するとされています。

:::message
上記のプラグインはすべてGitHub上で実在を確認しましたが(READMEの内容を要約しています)、実際に導入して動作を検証したものではありません。開発の活発さ・メンテナンス状況・対応バージョンなどはご自身でリポジトリを確認の上、判断してください。
:::

つまり、「AIエージェントの状態を可視化する」というアイデア自体はHerdr固有のものではなく、tmux/zellijのコミュニティでも同時多発的に同じ課題感からプラグインが作られている、というのが実態のようです。違いは、Herdrはこれを外部プラグインではなく**本体組み込みの一級機能**として提供している点にあります。フックへの追加設定なしに主要なエージェントを検知できる(ように見える)点は、プラグインを個別に選定・設定する必要があるtmux/zellijに対するHerdrのアドバンテージと言えそうですが、裏を返せば「対応エージェントの追加・カスタマイズの柔軟性」は、プラグインエコシステムが厚いtmux側に分があるとも考えられます。

## まとめ

Herdrは、`tmux`・`screen`・`zellij` が持っていた「ペイン・タブ・セッションの永続化」というモデルはそのままに、そこへ「どのAIエージェントが動作中/待機中/ブロック中か」を可視化する層を足した、AIコーディングエージェント時代を意識したターミナルマルチプレクサです。単一のRustバイナリで動作し、既存のターミナルエミュレータ(WezTerm、iTerm2、Kittyなど)の上で動く点も、乗り換えのハードルを下げる工夫だと感じました。

複数のAIエージェントを並列で走らせる機会が増えている方は、既存の `tmux` 環境に置き換えるかどうかは別として、一度公式サイトを覗いてみる価値はありそうです。
